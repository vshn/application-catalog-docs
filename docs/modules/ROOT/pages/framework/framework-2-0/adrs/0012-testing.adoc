## Problem Statement

All parts of the framework have to be tested.
Each part needs different tooling and approaches to make testing easier.
Special considerations have to be made in various parts of the framework apart from the tooling to be used to make testing as seamless as possible.

## High level goals

- Make sure multiple versions of a service with breaking changes can be deployed and tested on the same cluster
- Specifing the tooling
- What should be tested and how

## Proposals

### Parallel testing

One of the biggest issues with working with Operators and CRDs in K8s is that they are singletons.
While there are ways to make breaking changes seamles(ser), it's too much effort for simple tests.

Chrysopoeia generates distinct API groups based on the name of the `CustomResourceDefinitionSource`.
Chainsaw tests in the reagent (service chart) repositories leverage this behaviour by adding an ID part to the generated sources.
That ID is the `values.yaml`'s content hashed together with the claim namespace.
Since chainsaw generates a random namespace for each of the tests, every single e2e test run will have it's own set of CRDs to work with.
This is even true when chainsaw runs tests in parallel in various namespaces.

### Tooling

There are multiple layers to testing and each one needs one or multiple tools to help with it.

https://github.com/kyverno/chainsaw[Chainsaw] is the more powerfull successor to the previously used Kuttl testing.
It fixes most of the pain points of Kuttl which makes it a very comfortable tool to do e2e tests with K8s.

https://book.kubebuilder.io/reference/envtest.html[envtest] is the de-facto integration test tooling for kubebuilder projects.
It helps spinning up enough k8s to test parts of a controller.

https://github.com/helm-unittest/helm-unittest[Helm unittests] provide unittesting for Helm charts.
The concept is similar to Chainsaw and Kuttl.
It renders the chart and there are assert and matching rules to match the output against.

### What and how to test

Reagents bring a default set of CI which triggers a default Chainsaw test on each PR.
The default Chainsaw test works out of the box and simply checks if the helm chart installs or not.
A Service Maintainer can then add service specific asserts or even whole new steps to test advanced topics, like scaling, backup or restore.
Either unittests or golden tests should be maintained for each service.

Controllers should have integration and unittests.
These should run on every PR via CI and on the release CI as well.
Chainsaw e2e tests should be added to controller if sensible.
